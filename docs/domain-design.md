# 물류 MSA — DDD Aggregate 설계

> **목적:** 팀원들이 동일한 기준으로 Aggregate 경계를 판단하고 서비스별 설계 근거를 공유합니다.
> **참고:** API와 테이블의 세부 정의는 팀 SA 명세를, 응답·감사 규칙은 [공통 규약](common-contracts.md)을 참조합니다.
> **표기:** `[명세]`는 기존 요구사항, `[설계안]`은 제안한 경계, `[결정 필요]`는 팀의 추가 합의가 필요한 내용입니다.

## 1. 공통 개념과 판단 기준

- **Bounded Context:** 도메인 용어와 모델이 일관된 의미를 갖는 경계입니다. MSA 서비스 경계와 반드시 일치하는 것은 아닙니다.
- **Aggregate:** 함께 일관성을 유지해야 하는 도메인 객체들의 경계입니다.
- **Aggregate Root:** Aggregate 외부에서 상태를 변경할 때 진입점이 되는 대표 객체입니다.
- **불변식(Invariant):** 정상적인 상태 변경 전후에 반드시 만족해야 하는 도메인 규칙입니다.

Aggregate는 **어떤 규칙을 함께 보호해야 하는지**, **어떤 객체가 변경을 책임지는지**, **서로 독립적으로 변경할 수 있는지**를 기준으로 나눕니다. 테이블의 연관 관계나 Repository 개수만으로 결정하지 않습니다. 동시 요청이 발생하는 규칙은 DB 제약조건이나 잠금 등을 통해서도 보호해야 합니다.

## 2. Aggregate 경계 판단 예시

### Company / Product — 분리하는 설계

[명세] `Product`는 `company_id`로 소속 업체를 참조합니다. 업체 주소 변경과 상품 가격 변경은 독립적으로 발생할 수 있으므로, **[설계안]** `Company`와 `Product`를 각각 Aggregate Root로 둘 수 있습니다. 다만 상품 등록·수정 시 업체 존재 여부와 관리 권한을 확인할 책임은 별도로 정해야 합니다.

### Delivery / DeliveryRoute — 함께 묶는 설계

[명세] `Delivery`는 배송 상태를, `DeliveryRoute`는 배송 구간별 상태를 관리합니다. 배송 취소 시 관련 경로도 일관되게 취소해야 한다면, **[설계안]** `Delivery`를 Root로 두고 `DeliveryRoute`를 내부 Entity로 관리할 수 있습니다. 이는 가능한 설계의 예시이며, 최종 경계는 Delivery 담당자가 결정합니다.

두 예시는 **객체들이 연관되어 있는지**보다 **함께 지켜야 하는 규칙이 있는지**에 따라 경계가 달라질 수 있음을 보여줍니다.

## 3. 서비스별 Aggregate 설계

각 담당자는 Aggregate Root 후보, 포함 객체, 핵심 규칙, 경계를 나눈 이유를 작성합니다. 하나의 서비스에 Root가 여러 개라면 행을 추가합니다. 다른 서비스의 Aggregate 경계는 해당 담당자가 검토하여 확정합니다.

| 서비스 | Root 후보 | 포함 객체 | 핵심 규칙 | 경계를 나눈 이유 |
|---|---|---|---|---|
| Users | `User` | Root 단독. `UserRoleEnum`은 사용자 내부의 역할 값이며 별도 Aggregate가 아닙니다. | [명세] username은 중복될 수 없고 비밀번호는 해시로 저장합니다. [설계안] 일반 사용자(`USER`)는 업체 또는 허브 중 정확히 하나에 소속되며, 탈퇴한 사용자는 로그인할 수 없습니다. | [설계안] 계정·자격 증명·역할·소속·배송 담당자 여부의 변경과 삭제가 한 사용자 생명주기에 속합니다. 업체·허브는 다른 서비스가 소유하므로 ID로만 참조하고 Users Aggregate에 포함하지 않습니다. |

| Hub / Stock | `Hub` | Root 단독 | [명세] 17개 고정 허브의 기준정보를 제공하며 생성·수정·삭제 API는 제공하지 않습니다. | [설계안] 허브 기준정보는 재고 변경과 독립적으로 관리합니다. |

### Users 설계안

`User`를 단일 Aggregate Root로 둡니다. 현재 사용자 모델에 별도의 자식 Entity가 없으므로 포함 객체는 없습니다. `UserRoleEnum`과 업체·허브 ID는 사용자 상태를 표현하는 값 또는 외부 참조이며, 각각 별도 Aggregate로 Users가 소유하지 않습니다.

- [명세] username은 사용자 식별자로 중복될 수 없습니다. [결정] 탈퇴·삭제한 사용자의 username도 재사용할 수 없습니다. DB 유니크 제약이 삭제된 행에도 적용되며, 가입·생성 시 중복 확인도 삭제된 사용자를 포함합니다.
- [설계안] 비밀번호 해시, 역할, Slack ID, 업체/허브 소속, 배송 담당자 여부는 사용자 계정의 일부로 `User`가 변경을 책임집니다. 원문 비밀번호는 저장하지 않습니다.
- [설계안] `USER`는 업체 또는 허브 중 정확히 하나에 소속되고 둘 다 또는 둘 다 아닌 상태를 허용하지 않습니다. 업체·허브 존재 여부 확인은 각 소유 서비스에 조회하며, 해당 객체 자체는 Users Aggregate에 넣지 않습니다.
- [공통 규약] 삭제는 감사 필드를 기록하는 논리 삭제이며, 삭제된 사용자는 조회·로그인 대상에서 제외합니다.
- [결정] 공개 회원가입은 역할을 입력받지 않고 `USER`로 생성합니다. 요청에 `role`이나 `is_delivery_staff`를 추가해도 권한을 부여하지 않습니다. `MASTER` 생성과 역할 변경은 관리자 API로만 수행합니다.
- [결정] `MASTER`는 업체·허브 중 최대 하나에 소속되며 무소속도 허용합니다. 둘 다 소속되는 것은 역할과 관계없이 허용하지 않습니다.
- [결정] 사용자 목록·개별 조회·생성·수정·삭제는 `MASTER` 전용이며, 본인 조회·탈퇴는 `/api/users/me`로 합니다. 마지막 `MASTER`의 탈퇴·삭제는 막지 않습니다.
- [결정] `MASTER`는 수정 API로 비밀번호와 배송 담당자 여부도 바꿀 수 있습니다. 역할·배송 담당자 여부가 바뀌면 Gateway가 기존 토큰을 거절하지만, 비밀번호 변경만으로는 기존 토큰이 만료 전까지 유효합니다.

### Hub / Stock 설계 결정 사항

`Stock`은 허브·상품별 재고 수량의 불변식을 보호합니다. 주문별 재고 작업 Aggregate는 두지 않습니다. 실패·취소에 따른 복원 조정은 향후 메시징 연동에서 다루며, 실제 재고 수량 변경은 허브 서비스가 담당합니다.
